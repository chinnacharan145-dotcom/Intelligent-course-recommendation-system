1. Database Architecture Overview

The database is designed as a normalized academic, student, skill, career, course, assessment, recommendation, learning and analytics database. The core intelligence loop is:

Student Academic Profile → Skills → Interests → Career Goal → Courses → Prerequisites → Recommendations → Learning → Assessment → Skill Update → New Recommendations

Database Design Philosophy

Use approximately Third Normal Form (3NF) for transactional data.

Separate master/reference data from student transactions and learning events.

Use junction tables for many-to-many relationships instead of comma-separated strings.

Keep recommendation component scores separately so recommendations are explainable.

Use foreign keys and unique constraints to maintain referential integrity.

Design Django models in a database-agnostic way so SQLite can be used for development and PostgreSQL for production.

15. Recommendation Intelligence Data Flow

STUDENT  ↓StudentProfile  ↓Skills + Interests + Career Goals + Academic Context  ↓Recommendation Engine  ↓Candidate Courses  ↓Career Match + Interest Match + Skill Relevance + Content Similarity+ Branch Match + Semester Suitability + Difficulty Match  ↓Prerequisite Evaluation / Penalty  ↓Final Recommendation Score  ↓Ranked Courses + Explainable Evidence  ↓Student Interaction  ↓Enrollment / Learning Activity / Assessment / Feedback  ↓Student Skill Update  ↓Recommendation Recalculation

This closed-loop architecture turns the project into an adaptive recommendation platform instead of a static course-search application.

19. Important Design Improvements

CurriculumSubject is essential because the same subject can appear differently across regulations and curricula.

Recommendation stores component scores and explanation JSON so the UI can answer “Why was this course recommended?”.

RecommendationEvent captures user behavior for future recommender improvements.

CoursePrerequisite and SkillPrerequisite should be separate because course dependencies and skill dependencies represent different concepts.

Course source_url and last_verified_at support external course-data maintenance.

StudentSkill.source distinguishes self-reported proficiency from assessment-derived or system-inferred proficiency.

20. Final Database Architecture

The final database can be viewed as seven connected intelligence layers:1. ACADEMIC LAYER   University → College → Program → Branch → Regulation → Curriculum → Semester → Subject2. STUDENT LAYER   User → StudentProfile → StudentSkill / StudentInterest / StudentCareerGoal3. KNOWLEDGE LAYER   Skill → SkillPrerequisite   Career → CareerSkill / CareerInterest / CareerBranch4. COURSE LAYER   Provider → CourseCategory → Course   CourseSkill / CourseCareer / CourseInterest / CourseBranch / CoursePrerequisite5. ASSESSMENT LAYER   Assessment → Question → Option   AssessmentAttempt → StudentAnswer6. RECOMMENDATION + LEARNING LAYER   Recommendation → Feedback   Enrollment → Bookmark → LearningActivity7. INTELLIGENCE + GOVERNANCE LAYER   RecommendationEvent → analytics   AuditLog → administrative traceabilityCore loop:Academic Data + Student Data + Skill Data + Career Data + Course Data+ Assessment Data + Learning Data + Recommendation Events→ Intelligent Course Recommendation Engine.
